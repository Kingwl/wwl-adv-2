# 设计：塔操作菜单和直接升级

## 状态

Implemented

## 背景

Prototype 需要一个玩家可触达的塔成长模型。两次点击合成在尚未实现随机召唤、背包或格子压力前，与直接升级的玩家感知差异很小，但会引入源塔选择、兼容目标高亮和双格 mutation。当前阶段优先选择更小、更清晰的塔操作菜单。

## 目标

- 点击已放置塔后，在塔右上方显示浮动操作菜单。
- 菜单提供 `Upgrade` 和 `Remove`。
- 升级数值按塔类型和 tier 配置化，并已迁移到 `game/data/towers/towers.json`。
- 拆除返还 50% 建造和升级累计投入。
- 核心 mutation 保持在可测试规则层，场景只负责选择、布局和按钮路由。

## 非目标

- 不接入随机召唤或二合一合成经济。
- 不做复杂环形菜单、拖拽菜单或塔移动。
- 不新增专用美术资产；复用当前 Frost RTS UI frame 和 button 样式。

## 方案

`TowerConfig` 从 `game/data/towers/towers.json` 读取 tier 配置，包括伤害、射程、攻速、投射物参数、`effects[]` 和升到下一 tier 的费用。当前四种塔都是 3 级：

- Single：提升单体伤害、射程和攻击间隔。
- Area：提升伤害、射程、攻击间隔和溅射半径。
- Slow：提升伤害、射程、攻击间隔，并增强减速倍率和持续时间。

`TowerPlacementService` 承接升级和拆除：

- `try_upgrade_tower(tower_id)` 校验存在、未满级、金币足够后扣费，并更新 tower tier 和累计投入。
- `try_remove_tower_at(position)` 校验棋盘 occupant 和 registry 后移除塔，并按累计投入的 50% 返还金币。

`BoardView` 记录当前选中的棋盘塔，点击已占用格显示菜单，点击空格、道路格、暂停、重开或胜负流程时关闭菜单。`BoardHudController` 程序化创建 `Hud/TowerActionPanel` 和两个按钮，并按棋盘格位置把菜单 clamp 到视口内。

## 替代方案

- 两次点击合成：保留在历史设计中，但 Prototype 暂不采用，因为当前内容没有随机召唤或塔池压力来支撑合成差异。
- 直接点击塔立即升级：交互最短，但无法容纳拆除，也缺少确认状态。
- 底部固定塔详情面板：响应式更稳，但移动横屏会挤压已有塔卡区域。

## 风险

- 浮动菜单容易遮挡棋盘；native UI smoke 已增加菜单 crop/overlay，覆盖桌面、移动横屏和方形视口。
- 敌人和波次配置仍在 GDScript 中；MVP 继续推进敌人和波次数据文件时应迁移。
- 拆除返还使用向下取整；这是当前经济规则的一部分，后续平衡可以调整。

## 开放问题

- 未来引入随机召唤后，直接升级是否与合成并存，还是被合成替代。
- 升级费用和返还比例是否进入难度或关卡配置。
