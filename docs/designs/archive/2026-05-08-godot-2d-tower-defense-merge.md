# 设计：Godot 2D 塔防合成游戏

## 状态

Draft

## 背景

项目目标是用 Godot 制作一个 2D 塔防合成类游戏。核心体验需要同时成立：

- 塔防：敌人按路径推进，玩家通过布置、升级和组合防御塔阻止敌人到达终点。
- 合成：玩家把相同或兼容单位合成为更高阶单位，形成局内成长和策略取舍。
- 可测试：核心规则要能脱离 Godot 场景运行，便于测试驱动开发。

## 产品循环

1. 准备阶段：玩家消耗资源召唤或购买基础塔。
2. 合成阶段：同阶、同类或规则允许的塔可以合成为更高阶塔。
3. 防守阶段：敌人按波次沿路径移动，塔自动索敌和攻击。
4. 结算阶段：根据存活、击杀、连胜或波次奖励资源。
5. 成长阶段：解锁塔池、词条、被动、关卡修正或永久升级。

## MVP 范围

- 单地图、单路径、固定格子放置。
- 至少 3 个基础塔类型：单体、范围、减速。
- 1 条合成规则：两个同类型同阶塔合成一个高一阶塔。
- 至少 8 波敌人，包含普通敌人、快速敌人和高血量敌人。
- 基础经济：初始资源、击杀奖励、波次奖励、召唤费用。
- 失败条件：生命值归零。
- 胜利条件：完成全部波次。
- 可重复测试的确定性战斗模拟。

## 非目标

- MVP 不做联网、PVP、内购、存档云同步。
- MVP 不做复杂随机词条系统。
- MVP 不追求最终美术品质，先使用占位素材。
- MVP 不把战斗规则写死在场景节点里。

## 架构

核心原则：游戏规则和 Godot 表现层分离。

```text
Godot Scenes / UI
        |
        v
Scene Adapters
        |
        v
Game Core
├── Board / Slots
├── Tower / Merge Rules
├── Enemy / Wave Rules
├── Combat Simulation
├── Economy
└── RNG / Deterministic Clock
```

## 技术方向

- 默认使用 Godot 4.x + GDScript。
- `scripts/core/` 中的战斗、合成、经济、波次、随机数规则应尽量保持为 `RefCounted` 规则类，不直接依赖场景树。
- Godot 节点负责渲染、输入、动画、音效和把场景事件转发给核心规则。
- 所有影响战斗结果的随机行为必须使用可注入 seed 的随机数接口。
- 模拟层使用固定 tick，不依赖真实帧率，避免测试不稳定。
- 使用 GUT 跑 GDScript 单元测试和后续场景集成测试。

## 核心系统

### Board

- 固定大小格子。
- 格子状态：空、已占用、锁定、路径。
- 放置规则必须可单测：边界、占用、路径禁止放置、费用不足。
- 详细规则见 `docs/designs/2026-05-08-board-grid-rules.md`。

### Tower

- 字段：类型、阶级、攻击力、射程、攻速、目标策略、特殊效果。
- 行为：索敌、攻击、冷却、应用效果。
- 目标策略先支持：最近终点、血量最低、最先进入射程。
- 详细规则见 `docs/designs/2026-05-08-tower-types-framework.md`。

### Merge

- 输入：两个或多个 tower id。
- 输出：新 tower、消耗的旧 tower、可能触发的事件。
- MVP 规则：同类型同阶二合一，阶级 +1。
- 合成失败必须返回结构化原因，不能只返回 `false`。

### 敌人 And Waves

- 敌人字段：生命、速度、护甲、奖励、路径进度、状态效果。
- 波次字段：敌人列表、生成间隔、波次奖励。
- 波次生成和路径推进必须可被固定 tick 测试。

### Economy

- 资源变化必须通过统一服务产生，便于记录原因和测试。
- 经济事件：召唤、合成、击杀、过波、失败惩罚。
- 详细规则见 `docs/designs/2026-05-08-economy-resource-system.md`。

## Testable Rules

这些规则在实现前必须先写测试：

- 合成成功和失败条件。
- 塔的索敌优先级。
- 攻击冷却和伤害结算。
- 减速效果持续时间和叠加规则。
- 敌人按固定 tick 前进。
- 波次生成时间线。
- 资源不足时不能放置或召唤。
- 同 seed 下战斗结果一致。

## 开放问题

- 合成是否只允许同类同阶，还是允许配方合成。
- 玩家局外成长是 roguelite 式解锁，还是传统关卡推进。
- 是否需要移动端竖屏布局。
